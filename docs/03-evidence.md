# 03｜把已有经历变成可信证据

招聘方需要知道：你做过什么、能否独立重复、遇到新问题能否判断。证据不只来自大公司实习，研究、课程、开源和个人项目都可以使用，但必须保留各自的边界。

## 四种经历的整理方法

| 材料 | 应交付的证据 | 个人贡献怎样写 | 不能这样写 |
| --- | --- | --- | --- |
| 研究经历 | 研究问题、实验设计、论文或技术报告、复现实验 | 本人提出的假设、写的代码、负责的实验；共同贡献如实列出 | 把参与组会写成主导研究 |
| 课程作业 | 任务约束、课程允许公开的代码、独立扩展与复盘 | 团队分工、自己新增的实验和测试 | 删除“课程”标签伪装商业项目 |
| 实习 | 可公开的职责描述、脱敏方案、允许披露的结果 | 自己负责的组件与团队成果分开 | 上传公司数据、源码、内部面试题 |
| 开源贡献 | 原始 Issue/PR、讨论、合并状态、测试 | 明确修改、修复的风险、review 反馈 | 把 fork、翻译或运行教程说成项目作者 |

## 建一份事实账本

每一条简历主张对应一行：事实、证据位置、所属时间、数据口径、贡献边界、公开权限。例子：“实现本地分类 API”可以对应代码和测试；“服务 10 万用户”若没有获得授权的监控证据，就不能写。

团队项目的正确表达是“在四人课程项目中负责数据分割和评测模块，新增泄漏检查，提交链接为……”。不是“独立搭建完整 AI 平台”。没有量化收益时可以写功能、规模和边界，不必强凑百分比。

## 研究经历：用一个问题撑住整段陈述

按以下顺序准备一页材料：已有方法解决了什么；你发现什么缺口；你的可证伪假设；选择哪些对照；控制了哪些变量；结果是否稳定；哪些反例不支持你的解释；论文或实验中属于你的部分。

“我复现了论文”还要回答：使用哪个版本、哪些超参数不同、算力差异、数据处理差异、复现误差及原因。没达到原论文结果也可以是有价值的复现，前提是记录诚实且分析充分。不能把复现工作改名为新算法。

## 课程项目：从交作业到别人能用

先确认课程政策和组员同意公开的范围。删除私人路径、密钥和答案库；把依赖与输入写清楚；从空环境运行；补测试集说明；增加一个课程要求以外的对照或错误分析。README 首段保留“课程项目扩展”标签。

真正的增量可以很小：发现同一用户的数据同时出现在训练与测试；修复时间泄漏；把交互 notebook 变成可复现 CLI；实现一个模型不确定时的回退。关键是说明为什么改、如何验证，不是代码行数。

## 实习：既保密，也能说明能力

用职责和技术取舍表达能力。若不能披露业务数据，可以设计结构相同、数值不同的合成练习，但必须注明“公开教学重构，不是内部系统或真实业务数据”。不要声称合成实验产生了公司的业务结果。

可向前导师或负责人确认可公开范围；未获得确认时，只用已公开信息及允许表述的工作职责。公开许可和推荐信不是同一件事。对方同意推荐你，不代表允许公开其内部资料。

## 开源：选择能够被接受的小贡献

先读项目的 LICENSE、CONTRIBUTING 和维护者要求。找一个能复现的问题，提交最小复现，写能捕捉该问题的测试，再修复。个人说明列出 Issue、PR、测试结果和 review 意见。PR 未合并时写“已提交，等待 review”，不要写“已被采用”。

文档、翻译和测试贡献同样可以列出，但要对应目标岗位。系统岗更需要代码与可靠性证据；研究岗需要实验设计和模型分析；应用岗可以展示工具接入、任务评测和用户流程。

## AI 辅助的披露方式

记录工具、日期、用途、人工修改、验证和剩余不确定性。不要只写“AI 帮我写了代码”，也不要隐藏实质性生成。可以写：“AI 辅助生成初稿与测试候选；本人确定数据分割和评测方法，逐项运行、审查并修复错误。”

这句话必须与你实际做的事一致。只运行了教程，不能套用“本人确定方法”。面试中最直接的验收是：关闭助手，解释一段核心代码，修改一个需求，定位一个失败。不会的部分如实说明。

## 项目证据包的最小目录

| 文件 | 读者应知道什么 |
| --- | --- |
| README.md | 问题、快速开始、输出、验收与限制 |
| DATA_CARD.md | 数据来源、许可、粒度、标签和分割 |
| METHOD.md | 基线、方法、参数、对照与假设 |
| reports/ | 原始指标、失败样本、运行环境 |
| tests/ | 能捕捉真实错误的检查 |
| CONTRIBUTIONS.md | 个人、同伴、第三方和 AI 辅助贡献 |
| LICENSE / NOTICE | 自己的许可与第三方权利边界 |
